## Discrepancies between TMAIL-281 description and actual code

The ticket description references two things that don't exist in the codebase
as written. The spec validates the **actual** backend behaviour:

| TMAIL-281 says | Actual code | Where to verify |
|---|---|---|
| `GET /api/auth/me` to validate the token before/after signup | No `/api/auth/me` route exists. The protected-routes group returns 401 for ANY unknown URL because the auth middleware fires before the router can resolve the path. | `backend/src/router.rs` — grep for `auth/me`; the protected routes are listed starting line 110. |
| `POST /api/auth/login` returns `429` after lockout threshold | The lockout response is **HTTP 423 Locked** (not 429). `AppError::TooManyRequests` → 429 is reserved for the per-IP rate limiter; `AppError::AccountLocked` → 423 is the per-account lockout. | `backend/src/error.rs:80-100`; `services/auth_service.rs:247,280`; `migrations/073_account_lockout.sql` doc-comment. |

The spec uses `GET /api/imap-configs` as the equivalent "token works"
validation (returns 200 with `[]` for a brand-new account, 200 with the BYOK
row after provisioning). For the lockout assertion the spec checks
`status() === 423`.

## Per-IP auth rate-limit budget

The auth router enforces 10 requests / 60s / IP (`AUTH_RATE_LIMIT_MAX` /
`AUTH_RATE_LIMIT_WINDOW` — `router.rs:54-61`). Because the live backend sits
behind Apache + an SSH tunnel terminating on `127.0.0.1`, every browser request
shows up as the **same source IP**, so the entire suite shares one bucket.

The spec is structured around this:

- **Block 1** (`lockout describe`): runs first and burns ~8 of 10 slots
  (1 signup + 4 wrong via API + 1 wrong via UI + 1 correct via UI + 1 correct
  via API).
- **Block 2** (`UI surfaces describe`): a `beforeAll` hook calls
  `test.setTimeout(AUTH_RL_WINDOW_MS + 30_000)` and sleeps `AUTH_RL_WINDOW_MS`
  (default 65 s) so the per-IP window has fully reset before the rest of the
  suite hits the auth router.
- **Override:** set `E2E_AUTH_RL_WINDOW_MS=0` when running against a local
  backend that has the rate limit relaxed; the drain becomes a no-op.

First attempt did NOT split into two describes and hit a 429 on the final
signup of test 7. The split + drain is the load-bearing fix.

## Follow-up suggestions (out of scope for TMAIL-281)

- Consider routing BYOK-less accounts to `/onboarding` instead of `/app` after
  the *login* flow (not just signup). Today they land on `/app` and see two
  "Failed to load" error states — friendlier UX would be to push them back
  through the wizard. (Surfaced by the screenshot review above.)
- Apache's `X-Forwarded-For` is not parsed by the rate-limit middleware
  (`backend/src/middleware/rate_limit.rs:97-103`). Behind the live reverse
  proxy this means every real-user IP collapses to `127.0.0.1` and the
  rate limit is effectively a shared global cap. Worth wiring up the
  `axum-client-ip` crate or trusting `X-Real-IP` from Apache. Separate ticket.
- Add a smoke test that exercises the *lockout-window expiry*: wait
  `LOCKOUT_DURATION_SECS` + 1, retry with the correct password, expect 200.
  At a 15-min default duration this is impractical for CI but trivial to
  cover with a tunable `LOCKOUT_DURATION_SECS=5` env in a future spec.
