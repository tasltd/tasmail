| `req.extensions_mut().insert(claims)` | μs | |
| `next.run(req).await` | route-dependent | |

Each middleware hit takes ~1 Redis round trip + a few HMAC operations. No blocking DB query. No `unwrap()` (the only `parse` is on the UUID in the dead `set_rls_context` and the JWT decode result, both `?`-propagated). **Reviewed all three of the task's specific checks on the hot path:**

- **`unwrap` / blocking DB query / unindexed lookup**: none observed. JWT validation is in-process; Redis blacklist is one network hop; no DB query happens in the middleware.
- **Consistency of `claims.is_admin`**: see finding 5 — the helper exists, ~50% adoption.
- **`set_rls_context` once per query vs per request**: per request (in middleware), and currently a no-op — actual RLS happens lazily in `acquire_with_rls` inside the handler when it acquires its own connection. So "once per RLS-needing query" in practice, which is the right answer for a stateless connection pool (the alternative — pinning a connection per request for the entire request lifetime — would tank pool throughput).

## 10. Scalability hot-spot pattern recheck

The task asked specifically about scalability concerns in the auth subsystem. Walking the global scalability rule ("how does this scale at 10×–100× usage?"):

| Surface | At 10× users | At 100× users | Verdict |
|---------|--------------|---------------|---------|
| `/api/auth/login` | More Argon2 verifies → CPU bound at the worker level (Tokio worker pool is fine because each worker handles many connections; Argon2 verify is sync and CPU-blocking). Spawn-blocking would help. | Argon2 starts to be the dominant cost. Consider a dedicated CPU-bound worker pool, or hardware crypto. | OK at 10×, watch at 100× |
| `/api/auth/refresh` | Two DB writes (delete + insert session). Indexed on `refresh_token_hash`. Fine. | Same. | Fine |
| Token blacklist (Redis) | One Redis GET per request. Fine. | At 1k req/s, Redis becomes the bottleneck. Add in-process LRU (finding 22). | Fine at 10×, finding-22 at 100× |
| RLS `set_config` per RLS-needing query | One extra DB round trip per handler that uses RLS. | Same. | Acceptable; alternative (pin connection for entire request) is worse for pool throughput |
| WebAuthn challenge storage | Stored in `webauthn_credentials` itself with `'challenge:'` prefix and no expiry — orphan rows pile up forever. | At 100× users the orphan rows dominate the table. | Add background sweep or move to Redis with TTL |
| LDAP sync | Synchronous (finding 24) | Same — gets worse linearly with directory size | Spawn-to-background (finding 24) |
| Lockout state | Three columns on `mailboxes`; updated on every failed login. No issue. | Same — write-amplifies the row on attack but UPDATE is cheap. | Fine |
| SMS OTP table | Grows monotonically (`used = true` is set, row not deleted). | Old rows clutter the table; queries slow. | Add a periodic cleanup of rows where `expires_at < NOW() - INTERVAL '7 days'` |
