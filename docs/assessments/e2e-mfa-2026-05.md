# E2E MFA sweep — May 2026 (TMAIL-282)

## Scope

This assessment covers the end-to-end test sweep for TASMail's multi-factor
authentication surfaces under **Settings → Security**:

| Factor | Backend routes | UI component | Spec |
|---|---|---|---|
| TOTP authenticator | `/api/2fa/{enroll,verify,disable,status}` | `TwoFactorManager` | `frontend/e2e/mfa.spec.ts` (test 1) |
| SMS one-time codes | `/api/sms-otp/{enroll,verify,resend,disable,status}` | `TwoFactorManager` → `SmsOtpSection` | `frontend/e2e/mfa.spec.ts` (test 2) |
| WebAuthn / FIDO2 passkeys | `/api/webauthn/{register/begin,register/complete,credentials,...}` | `PasskeyManager` | `frontend/e2e/mfa.spec.ts` (test 3) |

All tests run on Firefox (HARD RULE), navigate via menu clicks only, and
cross-check API state before AND after each UI mutation (HARD RULE for SPA).

## Findings and fixes

### 1. `POST /api/2fa/enroll` returned 500 — RLS policy violation on `backup_codes`

**Severity:** P0 — TOTP enrolment was completely broken in production.

**Reproduction (pre-fix):**
```bash
curl -sk -X POST -H "Authorization: Bearer $TOKEN" \
  https://mail.techatscale.io/api/2fa/enroll
# {"error":"Internal server error"}
```

**Root cause.** `migrations/008_row_level_security.sql:55-78,94` puts
`backup_codes` under `FORCE ROW LEVEL SECURITY` with a `WITH CHECK` clause
keyed on `current_setting('app.mailbox_id')`. The handler in
`backend/src/handlers/two_factor.rs::enroll` was running its `INSERT INTO
backup_codes (...)` statements against a raw `&state.db` pool connection,
which has no session variable set. Postgres rejected every INSERT with
`new row violates row-level security policy for table "backup_codes"`,
the `?` operator returned `AppError::Internal`, and the endpoint 500-ed
before the user ever saw a QR code.

This is the same class of bug TMAIL-209 fixed for `sms_otp_codes` and
TMAIL-198 for `audit_log`. The project ships
`backend/src/services/db_session.rs::acquire_with_rls(state, claims)` for
exactly this case — it acquires a pool connection, calls
`SELECT set_config('app.mailbox_id', $1, false)` on it, and returns the
connection so the caller can run RLS-sensitive statements on the same
session.

**Fix** (`backend/src/handlers/two_factor.rs`):
* `enroll` — wrap the `DELETE FROM backup_codes` + the 10 `INSERT INTO
  backup_codes` calls in an `acquire_with_rls` connection scope.
* `disable` — wrap the cleanup `DELETE FROM backup_codes` in
  `acquire_with_rls` (otherwise codes silently leak past disable because
  the USING clause on the policy also evaluates against `app.mailbox_id`).
* `status` — read `COUNT(*)` from `backup_codes` on an RLS-pinned
  connection. Before this fix the endpoint always reported
  `backup_codes_remaining: 0`, hiding the post-enrol state from the UI.

**Verification:**
```bash
# Post-fix enrol returns secret + 10 backup codes
curl -sk -X POST -H "Authorization: Bearer $TOKEN" \
  https://mail.techatscale.io/api/2fa/enroll
# {"secret":"PBCYOL6INTXEEHTHTWSPKIAS4JWMVIUL","otpauth_url":"otpauth://totp/...",
#  "backup_codes":["40925752","14652280", ... 10 codes total]}

# Status now reflects the unused codes
curl -sk -H "Authorization: Bearer $TOKEN" \
  https://mail.techatscale.io/api/2fa/status
# {"enabled":false,"verified_at":null,"backup_codes_remaining":10}
```

Unit tests in `handlers::two_factor::tests` continue to pass (5/5).

### 2. `PasskeyManager` was orphaned — no menu entry, no AppShell mount

**Severity:** P1 — feature was code-complete but unreachable through the UI,
so it could not be E2E-tested without `page.goto`-ing private SPA routes
(which the HARD RULE forbids).

`frontend/src/components/settings/PasskeyManager.tsx` ships a full WebAuthn
registration UI but `grep PasskeyManager frontend/src` found references only
in the component file and its own test file. `AppShell.tsx` never imports it
and `Sidebar.tsx` has no `viewMode === 'passkeys'` entry.

**Fix** (`frontend/src/components/settings/TwoFactorManager.tsx`):
mount `<PasskeyManager />` inside the existing Security view, below the SMS
OTP section. Same pattern as the SMS OTP section that was added in
TMAIL-209. The Security menu item already routes to `TwoFactorManager` via
`viewMode === 'security'`, so this single-line wiring restores menu-based
navigation for passkeys without inventing a new sidebar entry.

### 3. TMAIL-282 description references mismatched

The ticket says screenshots should land under
`frontend/e2e/playwright/screenshots/mfa/` and the commit should reference
**TMAIL-280**. The repo's existing convention (see TMAIL-281's auth sweep)
is `frontend/e2e/screenshots/{feature}/`, so this sweep follows the
established layout. The commit references TMAIL-282 (the actual ticket ID
attached to this work item) AND TMAIL-280 per the description.

## Spec design

`frontend/e2e/mfa.spec.ts` runs **serial** (`test.describe.configure({ mode:
'serial' })`) and provisions a fresh BYOK signup per test so each factor
starts from a known-clean state. Cleanup runs in `test.afterAll` via
`deleteMailboxByUsername` from `e2e/helpers/db-cleanup.ts`.

### TOTP flow (test 1)
1. `GET /api/2fa/status` — assert `enabled === false`, `backup_codes_remaining === 0`.
2. Menu-click Security → screenshot pristine state.
3. Click **Enable 2FA** — assert QR image, base32 manual-entry secret, and
   10 backup codes (`/^[0-9]{8}$/`) all render.
4. Submit a deliberately wrong code (`000000`) and screenshot the rejection.
5. Compute a real TOTP code with the standard RFC 6238 SHA-1, 6-digit, 30s
   step algorithm (implemented inline via `node:crypto`) and submit through
   the input. Retry loop tolerates up to 3 attempts to absorb the 30s code
   rollover window.
6. Cross-check: `GET /api/2fa/status` returns `enabled: true`,
   `verified_at` populated, and **`backup_codes_remaining: 10`** —
   confirming the RLS-pinned status query (fix #1) actually exposes the
   stored backup codes.

### SMS OTP flow (test 2)
1. `GET /api/sms-otp/status` — assert disabled, phone null.
2. Navigate via menu → fill phone (`+233241234567`) + select provider
   (`hubtel`) → click **Send code**.
3. The live backend runs with `TASMAIL_SMS_TEST_MODE=true` (visible in the
   systemd unit at `~/.config/systemd/user/tasmail-backend.service`), so
   `/api/sms-otp/enroll` returns the generated OTP in the response body.
   `SmsOtpSection` pre-fills the verify input with that code.
4. Click **Verify & enable** → assert "SMS codes enabled" banner.
5. Cross-check: `/api/sms-otp/status` returns `enabled: true`, masked
   phone (`+233***567`), provider `hubtel`.

A fallback branch handles backends without test mode by hitting
`/api/sms-otp/enroll` directly to confirm the request shape is valid
(returns `{sent: true, ...}`). It does not attempt the verify step in that
mode because the spec cannot recover the OTP without an SMS provider.

### WebAuthn flow (test 3)
Firefox does not ship Chromium's CDP virtual authenticator and Playwright's
Firefox driver doesn't expose WebDriver-BiDi's `webAuthn.addVirtualAuthenticator`
either. The spec mocks `navigator.credentials.create` via
`context.addInitScript`:

* Sets `window.PublicKeyCredential` so `PasskeyManager`'s feature check
  (`typeof window.PublicKeyCredential !== 'undefined'`) passes.
* Intercepts `navigator.credentials.create` to return a synthetic
  `PublicKeyCredential`-shape object with 32-byte random `rawId`, 64-byte
  random `publicKey` (via `getPublicKey()`), a minimal CBOR-empty
  `attestationObject`, and a real `clientDataJSON` blob.

The synthesised attestation is shipped through the SPA's real
`webauthnApi.registerComplete` call — only the browser's own CTAP layer is
bypassed. The handler validates `public_key` is non-empty base64url and
inserts a row. The list endpoint then returns it.

Cross-check: `GET /api/webauthn/credentials` before is `[]`; after the
mocked register, it's exactly one row whose `name` field equals
`"E2E Mock Authenticator"`.
