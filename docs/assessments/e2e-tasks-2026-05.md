## 1. Test 1 — Tasks: full UI lifecycle round-trip

**Path:** Sidebar (apps group) → `[data-nav-key="tasks"]` → AppShell flips
`viewMode='tasks'` → `TaskManager` mounts.

The test creates a brand-new BYOK account, attaches the noreply IMAP server so the
sidebar's FolderTree paints, and then drives the TaskManager UI end-to-end:

1. **Baseline GET** `/api/tasks` → empty list, "No tasks yet" empty state visible.
2. **Click "Add Task"** → inline `TaskForm` opens with the "New Task" heading.
3. **Fill** title (`E2E Task ${RUN_TAG}`), description, set priority `high` via
   the native `<select>` → screenshot `tasks-form-filled.png`.
4. **Submit** the form (form's `button[type="submit"]:has-text("Add Task")`).
5. **Cross-check** GET `/api/tasks` → one row, `priority: "high"`,
   `completed: false`. Screenshot `tasks-list-after-create.png`.
6. **Toggle complete** via the `<Square>` checkbox button → button title flips
   to "Mark incomplete". GET `/api/tasks?completed=true` returns one row with
   `completed_at` set. Screenshot `tasks-after-toggle-complete.png`.
7. **Filter tabs:**
   - "active" → "No active tasks" empty state. Screenshot
     `tasks-active-filter-empty.png`.
   - "completed" → our row reappears. Screenshot `tasks-completed-filter.png`.
8. **Delete** via `button[title="Delete task"]` → "No completed tasks" empty
   state. Final GET `/api/tasks` returns an empty list.

### What this proves

- `[data-nav-key="tasks"]` is wired to `viewMode='tasks'` in the registry-driven
  Sidebar (TMAIL-398).
- The `tasks` view-mode branch in `AppShell.tsx:149` lazily mounts
  `TaskManager.tsx`.
- The inline `TaskForm` + the toggle + the delete trash icon all hit the four
  CRUD endpoints behind `/api/tasks` (`handlers/tasks.rs:30–122`).
- React-Query invalidation on every mutation keeps the UI list in sync with the
  backend within one tick.
- The completion filter query (`?completed=true|false`) is honoured by the
  list endpoint.

## 2. Test 2 — Auto-reply: SettingsHub → Mail → Vacation Responder

**Path:** Sidebar → `[data-nav-key="settings-hub"]` →
`[data-testid="settings-category-mail"]` →
`[data-testid="settings-section-vacation"]` → `VacationResponder` mounts inside
`[data-testid="settings-hub-pane"]`.

The test:

1. **Baseline GET** `/api/auto-reply` → returns `null` (no rule on a fresh
   account). Screenshot `autoreply-pristine.png`.
2. **Enable** the responder via the "Enable vacation responder" checkbox.
3. **Fill** subject (`On Holiday — TMAIL-288 ${RUN_TAG}`), body text, and start
   / end `datetime-local` inputs (start ≈ now + 1h, end ≈ now + 7d).
   Screenshot `autoreply-form-filled.png`.
4. **Save** — click "Save Settings" AND `waitForResponse` on the actual
   `PUT /api/auto-reply` request. Assert HTTP < 300 on the PUT before doing the
   GET round-trip. Screenshot `autoreply-after-save.png`.
5. **Cross-check** GET `/api/auto-reply` → returns a non-null
   `AutoReplyRule` whose `enabled`, `subject`, `body_text`, and `start_date <
   end_date` all match what we typed.
6. **Enable toggle stays checked** after save (sanity that the form's
   `useEffect` re-syncs state from the response). Screenshot
   `autoreply-active-state.png`.

### Why we wait on the network, not the "Saved!" label

The first iteration of this spec asserted the button text flickered to
`"Saved!"` after the click. That label only stays for 2 seconds before
reverting to `"Save Settings"`, so the assertion was racing the React-Query
invalidate-then-refetch and the GET round-trip would occasionally fire before
the PUT had landed in Postgres, returning `null`.

The current version uses
`page.waitForResponse((r) => r.url().includes('/api/auto-reply') && r.request().method() === 'PUT')`
so we know the backend has actually persisted the rule before the GET round-trip
runs. Standard Playwright pattern — see `composer.spec.ts:122` for the same
idiom.

### Selector hardening — scope everything to the SettingsHub pane

The first run of this test sent the subject text to the wrong input because the
unscoped `input[type="text"]` selector matched the global TopBar search box
before it matched the VacationResponder's subject field. The fix is to scope
every locator inside the test to `page.getByTestId('settings-hub-pane')`:

```ts
const pane = page.getByTestId('settings-hub-pane');
await pane.locator('input[type="text"]').first().fill(subject);
await pane.locator('textarea').fill(bodyText);
await pane.locator('input[type="datetime-local"]').nth(0).fill(startStr);
```

This is the same pattern the `contacts-templates-filters.spec.ts` sweep already
uses for SettingsHub sections and the only durable way to avoid coupling the
spec to AppShell's TopBar internals.

## 3. Test 3 — Quota bar: sidebar paint + API coherence

**Path:** The QuotaBar lives in `Sidebar.tsx:96` and renders unconditionally
for any logged-in user — there is no menu click to drive. The test instead
asserts:

1. **GET `/api/quota`** returns a `QuotaStatus` with all four numeric fields
   (`quota_bytes`, `used_bytes`, `usage_percent`, `quota_warn_percent`) finite
   and `quota_bytes > 0` (signup provisions the default quota).
2. **`.quota-bar` is visible** in the sidebar within 15s of landing on `/app`.
3. **TMAIL-417 NaN regression guard** — the bar's `textContent` matches
   neither `/NaN/` nor `/undefined/`. The bar must paint a usable "X B used /
   Y B" label or hide itself completely, never a half-rendered
   "NaN undefined" string.
4. **POST `/api/quota/sync`** returns 200 with a finite `usage_percent` and
   `quota_bytes > 0`. The handler at `handlers/quota.rs:53` is now BYOK-aware
   (TMAIL-156) and falls back gracefully when the user's IMAP server doesn't
   support the `QUOTA` extension.
5. **Reload** the page so the sidebar picks up the synced state, then screenshot
   `quota-bar-after-sync.png` for the audit trail.
6. **Type-shape assertions** — `is_warning` and `is_over_quota` are typed as
   booleans so any future state-injection spec has a stable contract to test
   against.

### Why warning / over-quota states are not driven live

The issue spec calls for screenshots of the quota bar in **low / warning /
over-quota** states. Forcing the bar into warning / over-quota in an E2E run
requires either:

- (a) uploading enough real attachments to exceed the configured
  `quota_warn_percent` (90% default), which would take dozens of GB on the
  live tunnel, or
- (b) injecting fake `quota_usage` rows directly into Postgres via
  `helpers/db-cleanup.ts`, which the spec deliberately avoids because the
  cleanup script is a thin psql wrapper without an upsert path for the
  `quota_usage` table.

Both options are out of scope for this sweep. The current test still captures
the **baseline** screenshot, asserts the API contract, and proves the bar
*paints* with no rendering bugs. A follow-up task (see below) should add a
test-only `POST /api/_test/quota/inject` endpoint to drive the warning /
over-quota states deterministically.

## Composer banner gap (documented, not fixed in this sweep)

The issue spec also calls for an **"auto-reply active banner in composer"** —
a UI affordance that warns the sender they have an active vacation responder
when they hit Compose. As of TMAIL-288 HEAD:

- `Composer.tsx` does NOT read `/api/auto-reply` on mount.
- No banner / toast / inline notice surfaces when the user composes a message
  while their vacation responder is active.

This is a real product gap, not a spec bug. The current spec captures the
**active state** of the Vacation Responder (`autoreply-active-state.png`) so
the audit trail shows the responder is enabled end-to-end; adding the banner
itself is a separate work item.

**Follow-up:** file `TMAIL-NNN — Compose: show "Auto-reply is active" banner
when /api/auto-reply.enabled is true` as a child of TMAIL-288. The banner
should hit `GET /api/auto-reply` lazily on Composer mount (React-Query already
has the `['auto-reply']` query key cached if the user just visited the
SettingsHub).
